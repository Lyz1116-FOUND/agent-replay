# Backend API & Prompt Evaluation

This document describes the FastAPI service layer and the prompt-optimization
experiment harness added on top of the Agent Replay recorder. Both reuse the
same execution and trusted-verify logic as the CLI, so every number is
reproducible and auditable.

## Architecture

```
Task → Agent → Execution → Patch → Tests → Evaluator → Replay / Report

        ┌─────────────────────────────────────────────────────┐
        │  agent_replay (Python)                              │
        │                                                     │
        │  core/executor.py  ── reuses the Node recorder via   │
        │        │              subprocess, mirrors trusted-   │
        │        │              verify from cli/validation     │
        │        ├── api/      FastAPI service (routers,       │
        │        │              services, schemas)             │
        │        └── prompts/  default/structured/verify.txt   │
        │                                                     │
        │  experiments/        prompt_eval + metrics + report  │
        └─────────────────────────────────────────────────────┘
                              │
                              ▼
        dist-cli/agent-replay.mjs  (Node recorder, unchanged)
```

The Python layer never reimplements agent execution: it invokes
`node dist-cli/agent-replay.mjs record` and reads the resulting
`agent-replay/v1` trace, then judges the task by running the task's own verify
command in the final worktree (`node --test`). Token usage is read from
`trace.metadata.usage`, which the recorder now preserves from the agent's
`step_finish` events (see `cli/adapters/opencode.ts`).

## API contract

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/tasks` | Create a task (`{task, prompt_template, repo?, metadata?}`). |
| `GET` | `/tasks/{task_id}` | Read task status and metadata. |
| `POST` | `/tasks/{task_id}/run` | Run the task synchronously; returns `{task_id, run_id, status}`. |
| `GET` | `/runs/{run_id}` | Read a run's result (`success`, `latency_ms`, `test_result`, `evaluation`, `usage`). |
| `GET` | `/health` | Health check for Docker/deployment. |

Interactive documentation is at `/docs` (OpenAPI/Swagger).

`task` must be a fixed task-set id (see below). Invalid task ids or prompt
templates return `400`; unknown stored ids return `404`. The run endpoint is
synchronous: a run may take tens of seconds to minutes and blocks the request
until the agent finishes.

## Prompt variants

Prompt templates live as standalone files in `agent_replay/prompts/` and are
rendered with `{{ instruction }}` substituted by the task's own instruction.

| Variant | File | Characteristics |
|---|---|---|
| A — default | `default.txt` | The task's bare instruction (no extra structure). |
| B — structured | `structured.txt` | Explicit goal, constraints, steps, mandatory test run, and output requirements. |
| C — verify | `verify.txt` | B plus: analyze before editing, run tests after, check for regressions, self-check before finishing. |

The experiment treats the prompt as the main variable; the task set, agent,
model, and environment are held constant.

## Fixed task set

Ten self-contained `node:test` exercises under `examples/tasks/` (3 original +
7 generated by `scripts/gen_eval_tasks.py`). Each has a `task.json`, a buggy or
empty source file, a `test.mjs`, and a `reference/` answer excluded from the
agent's workspace. `node dist-cli/validate.mjs --verify-tasks` proves every
task fails at baseline and passes with its reference fix.

| id | kind | baseline |
|---|---|---|
| single-file-bug | bug | 0 pass / 3 fail |
| multi-file-bug | bug | 1 / 3 |
| small-feature | feature | 0 / 1 |
| max-of-two | bug | 1 / 2 |
| reverse-string | bug | 1 / 2 |
| is-palindrome | bug | 2 / 2 |
| sum-array | feature | 2 / 1 |
| capitalize | bug | 1 / 2 |
| fibonacci | bug | 2 / 2 |
| dedupe | feature | 1 / 2 |

## Running the experiment

```bash
python -m experiments.prompt_eval \
  --prompts default,structured,verify \
  --tasks all --runs 1
```

For each `(prompt, task, run)` it runs the agent through the shared executor
and writes, under `results/<experiment_id>/`:

- `raw_runs.jsonl` — one line per run (full outcome).
- `config.json` — model, adapter, task set, commit, seed, timestamp.
- `summary.json` / `summary.csv` — per-prompt metrics.
- `report.md` — Markdown report with setup, results table, failure analysis,
  and a data-driven conclusion.

Metrics (`experiments/metrics.py`):

- **Success rate** — fraction of runs whose trusted verdict is `pass`.
- **Pass@1** — fraction of tasks whose *first* run passes (equals success rate
  when each task runs once).
- **Latency** — avg / median / p95 / min / max wall-clock.
- **Tokens** — summed/averaged input & output tokens; marked `unavailable` when
  the provider reports none (never fabricated).
- **Bootstrap 95% CI** for success rate (percentile bootstrap).

## Docker

```bash
docker build -t agent-replay .
docker run -p 8000:8000 agent-replay
curl http://127.0.0.1:8000/health   # {"status":"ok"}
```

The image bundles Node 22 (recorder), Python 3 (FastAPI), and git (recorder +
evaluator). The agent CLI itself (e.g. `opencode`) is **not** installed: real
agent runs require the user's own credentials, so mount them at run time if you
need `/tasks/{id}/run` to execute an agent.
